# Контракт данных и трассировка

Контракт описывает логические поля для подготовки отчёта, а не имена реквизитов 1С. Не требуй транзакционной детализации там, где для задачи достаточно сверенных месячных итогов; сохраняй известное зерно.

## Источники

Для каждой выгрузки: `source_id`, имя файла/отчёта, контур учёта, период, организации, фильтры, валюта, масштаб, признак НДС, дата получения, статус закрытия. В рабочей папке сохраняй неизменённую копию и при необходимости контрольную сумму. Не публикуй содержимое или приватные пути в репозитории навыка.

## Нормализованные строки

| Поле | Смысл |
|---|---|
| source_id, source_row_id | Трассировка до строки; ключ включает базу/организацию, когда номера пересекаются |
| period | Экономический месяц YYYY-MM, не обязательно месяц банковской оплаты |
| entity, site | Организация и площадка; неизвестная площадка остаётся неизвестной |
| scenario, version | actual / budget / forecast, версия бюджета или прогноза |
| source_article, pnl_article | Статья источника и статья P&L; отсутствие маппинга отмечается явно |
| amount, currency, unit_scale | Исходная сумма, валюта, множитель единиц; сохраняй исходные значения |
| normalized_amount | Преобразованная сумма с зафиксированными правилами знака, НДС и курса |
| recognition_basis | Основание признания и ссылка на методику |
| internal_flag, partner_entity, pair_id | Внутренние операции, сторона и пара для элиминации, когда применимо |
| treatment | include / exclude / unresolved; для exclude обязательна причина |

Заказ, продукт, количество, подразделение, постоянный/переменный характер и компоненты себестоимости нужны только для соответствующей аналитики. Не заполняй отсутствующие поля выдуманными значениями.

## Справочник маппинга

Ключ — сочетание полей источника, достаточное для однозначной классификации, с периодом действия. Храни целевую статью, применимость к организации, правило знака/НДС, обоснование и статус решения. Проверяй перекрытие правил: строка не должна попасть в две статьи. Привязка только по тексту назначения платежа — гипотеза, требующая проверки.

## Корректировки и распределения

У корректировки отдельный ID, период, сумма, исходная и целевая статья/площадка, причина, источник, статус согласования и, если требуется, период обратной записи. Повторный запуск не должен добавлять ту же корректировку второй раз.

Распределения веди отдельно: `allocation_id`, пул, сумма, получатель, значение базы, доля, распределённая сумма, остаток. Изменение базы создаёт воспроизводимую новую версию, а не скрытую ручную замену итогов.

## Контроль покрытия

Сверяй количество строк и суммы до/после преобразования в разрезах, где они сопоставимы. Переход от исходного итога к P&L покажи мостом: итог источника + корректировки знаков/НДС/периода/периметра − исключённые строки = нормализованный итог. Несопоставленные строки учитываются в мосте отдельно и не исчезают из контроля.

Не удаляй предполагаемый дубль только по равенству даты и суммы. Установи бизнес-ключ и отличие повторной выгрузки от самостоятельной операции. Строки итогов отчёта используй для сверки, не суммируй вместе с их детализацией.
